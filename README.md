# PyroSim / FDS Agent Workbench

Local Windows MVP: a small desktop configuration console plus a stdio MCP server for OpenCode. It uses the installed PyroSim/FDS binaries and keeps the model authoring interface on standard `.fds` files.

## Start

Install the desktop dependency once with `.venv\\Scripts\\python.exe -m pip install -r requirements.txt`, then run `start-workbench.cmd`. Set the PyroSim folder and a case workspace in Settings, then click **Save and inspect**. The MCP server is configured in the included `opencode.json`; copy that config into a project that OpenCode opens, or use `OpenCode > Install project config` from the console.

## Windows component installation

For the downloadable Agent/FDS/model packages and first-run setup, see [docs/INSTALLATION.zh-CN.md](docs/INSTALLATION.zh-CN.md). The public-release download and checksum-verifying PowerShell helper is `tools/install-components.ps1`. The optional offline Qwen installer bundles the GGUF and llama.cpp CPU/Vulkan runtime; no separate LM Studio/Ollama installation is needed for the built-in model.

## Windows installer

Run `powershell -ExecutionPolicy Bypass -File .\\build-windows.ps1` to build the self-contained portable runtime and `dist\\PyroSim-FDS-Agent-Setup.exe`. The package includes its own Python runtime and dependencies, the Qt desktop, stdio MCP server, Windows PyroSim UI Automation dependencies, `theng` results processing, and the SHA-256-pinned official TEMPERATURE example input. Staging that example does not require GitHub connectivity. The installer installs per-user under `%LOCALAPPDATA%\\Programs`, creates Start Menu and Desktop shortcuts, and registers an uninstaller. Launch diagnostics are written under `%LOCALAPPDATA%\\PyroSimFdsAgent\\logs`. PyroSim/FDS and OpenCode remain external prerequisites; configure their local executable paths in the workbench after installation. Preferences are stored under `%LOCALAPPDATA%\\PyroSimFdsAgent`.

The separate offline Qwen model installer is built with `.venv\\Scripts\\python.exe tools/build_local_model_installer.py --source <verified-agent-model-payload>`. The source folder must contain `agent_runtime/` and `licenses/` with the pinned Qwen3-0.6B GGUF and llama.cpp b11836 CPU/Vulkan server. The builder rejects size or checksum mismatches. The installer puts the model under the Agent install directory; the workbench starts it on loopback and automatically falls back from Vulkan to CPU.

The configured case workspace is the only area the MCP server can read or write. Existing source cases are copied before edits. FDS runs are launched only after an explicit `approved: true` argument.

The Settings panel's **Auto-detect invalid paths** action checks the saved values, `PYROSIM_ROOT` / `PYRO_FDS_CASE_ROOT`, OpenCode on `PATH`, Windows PyroSim registration, and standard install folders. It fills only invalid or empty fields and shows the source of each candidate; it does not crawl drives or save settings automatically. A valid configured folder remains authoritative, including when there are other installs. The OpenCode MCP config is generated from the active checkout at startup and passed as inline config content, so a copied `opencode.json` with an old E: checkout cannot override the active D: MCP path. This path binding is separate from discovery of the installed PyroSim and case workspace.

The Agent chat has an explicit, persisted execution-mode selector. OpenCode mode sends messages only to the OpenCode process and excludes the local-model provider from the OpenCode model picker. Local-model mode sends ordinary chat directly to the configured loopback model API without tools/MCP, and separately exposes the fixed TEMPERATURE workflow. Codex-plugin mode disables Qt message sending and directs work to the Codex host's plugin. Switching modes cannot re-route the current Qt message to a different host.

OpenCode subprocesses inherit existing `HTTP_PROXY`, `HTTPS_PROXY`, and `NO_PROXY` settings. If those proxy variables are absent, the companion reads the current user's static Windows Internet proxy setting and passes it only to the spawned OpenCode process, with loopback MCP addresses excluded. It does not change machine/user proxy settings or copy proxy credentials. PAC-only settings are not interpreted; configure proxy environment variables in that case.

## Current scope

### Adapter profiles and result presentation

`inspect_installation` and the separate `inspect_adapter_capabilities` MCP tool expose a version/capability profile. The FDS solver is marked `verified` only when a successful workflow record matches the exact solver executable and its revision is in the verification registry; an executable or version string by itself is reported as available but unverified. PyroSim UI profiles are resolved from the live window version (currently 2024.2); unknown versions are restricted to read-only probing, import/export are experimental, and native `.psm` editing is unsupported. Results display controls are independently marked experimental.

After a successful solve, `describe_result_presentation` emits a stable, read-only manifest for the `.smv`, field outputs, CSV, `theng` summary, and HRR plot. It marks artifacts `ready` when files belong to the completed workflow, while the PyroSim Results render status remains `not_verified` until a separate UI readback confirms it. This lets Agent hosts present the same result package without coupling FDS execution to unreliable GUI automation.

- Detect PyroSim/FDS/Smokeview and report detected paths, exact FDS revision evidence, and PyroSim UI profile state separately.
- List `.fds` cases in the configured workspace and copy a selected case to a new ID.
- Create an edited case in one operation: copy the source, apply only allowlisted FDS parameter updates, read the saved values back, and remove the new copy if verification fails.
- Inspect and update a conservative allowlist of FDS parameters.
- Compare key fields between two FDS cases read-only, including time controls and each mesh's IJK/XB values, to review a PyroSim GUI export round-trip.
- Run a read-only preflight over HEAD/TIME/MESH, cell counts, time range, and solver availability.
- Prepare a persistent workflow with a hash-verified input snapshot, explicit user approval, asynchronous FDS execution, live progress, status polling, and stop requests.
- Run FDS in an isolated case folder, capture logs, and summarize generated outputs.
- Post-process completed FDS workflows with the optional `theng` integration, writing a machine-readable summary and available HRR plots under each run folder.
- Open the completed workflow's `.smv` file in the installed PyroSim Results 3D viewer and report whether its window was detected.
- Expose the same operations to OpenCode through MCP tools.
- Choose an OpenCode model in the Qt companion, refresh the provider model list, and pass the selected `provider/model` on each conversation.
- Configure an optional loopback OpenAI-compatible local model endpoint and model ID. The companion checks `/v1/models` and probes structured tool calling before marking tool support as verified.
- Package the same FDS MCP workflows as a Codex plugin under `.agents/plugins/pyrosim-fds`, with a repo marketplace and a simulation workflow skill.
- Launch CC Switch from the companion and refresh the OpenCode model inventory after a provider switch. The companion does not edit CC Switch databases or credential-bearing provider files.

## Model settings and Codex plugin

The **本地模型编排** button is a first software-owned workflow for local models, based on the TubeSim phase-gate pattern. It uses a fixed allowlist for the official TEMPERATURE example: inspect the installation, stage the pinned case, inspect/preflight it, and freeze a workflow snapshot. The local model receives only a constrained `continue` / `stop` decision at phase gates; it cannot select MCP tools or invent arguments. FDS remains behind a separate Qt confirmation dialog. After approval the workbench starts and polls FDS, then asks the local model whether to continue to `theng` post-processing and Results inspection. A stop or malformed model response halts the next phase and reports the completed work. This is the initial fixed-example path; it does not yet translate arbitrary natural-language simulation requests into a general local workflow.

In the Qt panel, choose a model from **Refresh models** or type a `provider/model` ID. **Save model configuration** persists the choice, and each new OpenCode request receives it with `--model`. Optional local models use a loopback OpenAI-compatible `/v1` endpoint and the model's exact server ID. **Check connection and tool calling** reads `/v1/models` and probes a forced tool call. Tool support is only enabled in OpenCode after that probe succeeds. The generated config lives in `.runtime/opencode.generated.json`; the checked-in project MCP config and provider credential files are not rewritten. At runtime, an inline OpenCode config override ensures the MCP command uses the active checkout even when a copied project config points to an older folder.

The Codex plugin source is in `.agents/plugins/pyrosim-fds` and the repo marketplace is `.agents/plugins/marketplace.json`. On another machine, run `powershell -ExecutionPolicy Bypass -File .agents/plugins/pyrosim-fds/install-local.ps1` to point its MCP entry at that checkout's virtual environment. Add the repo marketplace from Codex's Plugins view or with `codex plugin marketplace add .agents/plugins`, then install/enable **PyroSim / FDS**. The plugin packages the workflow skill and the same local MCP server; the Codex host controls its own model selection.

CC Switch currently has no documented public CLI/API for reading or switching its active OpenCode provider; its app uses internal Tauri commands. The Qt integration therefore opens the app and refreshes OpenCode's available model list after a switch. It does not read CC Switch's database or overwrite key-bearing configuration.
- Open a `.psm` file from the configured case workspace as a hash-verified working copy in PyroSim; the source remains untouched.
- Optionally inspect the PyroSim 2024.2 UIA surface, take live UI snapshots before and after supported actions, and use the version-profiled UI bridge to import an FDS case into a new PSM copy or export a registered PSM copy into a new FDS case ID. UI steps are streamed to the Qt companion panel.
- Publish MCP tool and FDS solver events to the Qt companion panel while work is in progress. The chat transcript shows actual tool names, arguments, concise readbacks, and failures as they arrive; the activity strip remains available for the same events.
- In attached mode, use a compact stylesheet, shorter header labels, stacked environment cards, and wrap-anywhere text so paths and tool output remain readable in a narrow side pane.

PyroSim's `.psm` model is a Java-serialized binary format, and the installed Java 21 runtime has no JSR-223 JavaScript engine for the discovered internal script host. The MCP includes a separate, optional Windows UI Automation bridge (`pyrosim_agent_gui`) for PyroSim 2024.2. Install it with `.venv\\Scripts\\python.exe -m pip install -r requirements-ui.txt`. `pyrosim_ui_snapshot` reads a fresh UIA snapshot of the running PyroSim window and visible dialogs without launching the app or clicking controls; call it before and after supported actions for an observe-act-observe loop. `pyrosim_ui_inspect` can launch PyroSim and samples its UIA controls. `pyrosim_import_fds` stages an FDS copy in the configured workspace and imports/saves it as a new PSM copy. A real-window import and PSM Save As round trip succeeded for a disposable case. `pyrosim_export_fds` only accepts a PSM copy registered by that import operation and exports to a new, non-existing FDS case ID, then compares supported fields with the source. Export remains experimental: a real-window attempt returned `ElementNotEnabled` and exposed a `Warning` window, but its contents were not readable from the current UIA snapshot. The bridge depends on an interactive Windows desktop and a supported PyroSim 2024.2 UI profile. Neither title/file checks nor field comparisons establish full model-tree, geometry, CAD/BIM, or engineering equivalence. The Qt companion streams reported UI bridge steps and now distinguishes operation, success, and failure status; it does not inject controls into PyroSim's 3D view. `theng` remains a results-processing interface, not a confirmed `.psm` authoring API.

The workflow tools are `preflight_case`, `prepare_simulation`, `start_simulation`, `get_simulation_status`, `cancel_simulation`, and `list_simulation_workflows`. Use `create_case_with_updates` when preparing a modified case: it creates a new `.fds` copy, applies the supported parameter allowlist, and verifies the saved values before returning success. `create_case_with_burner_obstruction` adds one rectangular burner (`&OBST`) and its linked `&SURF HRRPUA` on a new case copy, checks that it fits within a parsed mesh boundary, and reads back the saved geometry and surface values. It does not check collisions with existing geometry or establish that the chosen fire and mesh are physically appropriate. `create_case_with_surface_updates` edits exactly one existing `&SURF` selected by `surface_id` on a new copy. Its only fields are `HRRPUA` (0–100000 kW/m²), `TMP_FRONT` (0–2000 C), `MASS_FLUX` (0–100 kg/m²/s), `VEL` (-100–100 m/s), and `THICKNESS` (0–10 m); existing scalar values are replaced in place, absent fields are appended, and all other record text and fields are preserved. Missing or duplicate matching SURF IDs are rejected, parsed readback and the unchanged source hash are checked, and any failure deletes only the copy created by that call. It cannot create `&SURF` records, edit other fields, or accept arbitrary FDS text. `create_case_with_obstruction_updates` replaces only `XB` on exactly one existing `&OBST` selected by `obstruction_id` on a new copy. It accepts six finite numeric bounds with strict `min < max` per axis, requires every source `MESH.XB` to be valid, and requires the new block to fit fully inside at least one mesh domain. Other record text and fields are preserved; parsed readback, stable record counts, unchanged non-target records (except the copied `HEAD.CHID`), and the unchanged source hash are checked, and any failure deletes only the copy created by that call. It cannot change IDs, `SURF` references, or other fields, and does not check geometry overlap. General geometry editing and arbitrary surface-field editing remain unsupported. Workflow preparation then freezes the exact input hash; starting FDS still requires explicit user approval. Workflow metadata and frozen inputs are stored under `.pyro_agent_workflows` inside the configured case workspace. Preflight is conservative and static; it does not replace the FDS parser, PyroSim model checks, or engineering review. The Qt panel displays solver progress as a progress bar when FDS emits parseable time-step lines; if no such lines appear, status and log events remain visible but percentage progress may be unavailable.

Optional results post-processing is provided by `analyze_simulation_results`. Install it into the project environment with `.venv\\Scripts\\python.exe -m pip install -r requirements-results.txt`. It accepts only completed workflow IDs, reads the associated `.smv` with Thunderhead's `theng`, and writes `analysis/summary.json` plus an interactive `analysis/hrr.html` when HRR output exists. This reports available output data; it does not add missing slice or device output retroactively.

The `open_simulation_visualization` MCP tool opens a successful workflow's `.smv` output in `PyroSimResults.exe` and checks for a visible viewer window. PyroSim's official 2024.2 workflow uses the separate PyroSim Results 3D viewer for FDS visualization; the main PyroSim application can launch it through Results > View Results. The Qt companion reports when the Results window opens. The tool does not modify the model or rerun FDS.

The Results UI MCP also provides `results_ui_inspect`, `results_ui_set_display`, `results_ui_set_time`, `results_ui_set_playback`, and `results_ui_adjust_speed`. These controls only target a visible Results window whose title matches a completed workflow's `.smv`; if duplicate windows exist, controls target the uniquely active one or stop with an ambiguity error. Time, playback state, and speed are read back from the Results status bar. Inspection returns compact tree paths, time controls, matching windows, and status text. `results_ui_set_display` locates exactly one item by its complete tree path, reads the item's context-menu `Show`/`Hide` command, performs only the requested idempotent action, then reads the inverse command back to verify the new state. Ambiguous paths or unavailable menu state fail closed without changing display. This confirms the Results item's application-level visibility command, not pixel-level rendering or engineering correctness. The official [Results 2024.2 manual](https://www.thunderheadeng.com/docs/2024-2/results/) documents the Show/Hide actions and indicates active items and their parents are bold.

On Windows, when no Intel MPI fabric has been selected in the process environment, the solver runner defaults to the local shared-memory fabric (`I_MPI_FABRICS=shm`). This avoids the bundled solver's OFI endpoint initialization failure seen in this restricted single-machine environment; an explicitly configured fabric remains untouched.

The PyroSim UI bridge is deliberately experimental until its full import/export path is exercised on a disposable case in the target interactive desktop. If a dialog does not match the supported profile, stop and use the normal PyroSim UI manually. `compare_case_inputs` only compares selected input fields; it does not verify complete geometry or model-tree equivalence. General `.psm` model editing remains unsupported: the file is a vendor-specific binary format and no stable public model-edit API has been verified. The FDS layer has bounded copy operations for adding a rectangular burner obstruction with a linked `HRRPUA` surface, for editing allowlisted numeric fields on one existing `&SURF`, and for replacing `XB` on one existing `&OBST` selected by ID. These operations do not provide arbitrary geometry or arbitrary surface-field editing and do not check geometry overlap. A complete `.psm` editor requires a vendor API or a separately verified PyroSim-specific adapter.
